# 2026 AI 先锋未来人才大赛复盘

## 1. 复盘目的

本文件将本项目未入围的经验转化为后续产品决策约束，避免复盘只停留在口头讨论。

它不修改已经冻结的报名样例数据，也不把公开入围推荐理由解释为官方淘汰意见。所有关于未入围原因的判断均为对公开材料与本仓库交付物的对比推断。

## 2. 数据来源与方法

- 来源：[AI 先锋未来人才大赛 - 大赛入围名单](https://bytedance.larkoffice.com/wiki/JNoOwxKT2iup6NkEBQzcY9lFnLe)
- 读取方式：飞书 CLI 只读获取完整 Wiki 文档，未依赖浏览器懒加载结果。
- 文档版本：Revision 79。
- 解析结果：309 条有效入围记录，覆盖 107 家命题企业。
- 安克创新：3 支入围队伍。

推荐理由关键词统计允许同一记录命中多个主题，只用于识别趋势，不等同于官方评分权重。

## 3. 安克创新入围方案对照

| 队伍 | 入围方案的主要优势 | 对本项目的直接启示 |
|---|---|---|
| token决定上限 | 以多智能体、证据驱动和红队质疑重构产品定义，并有实际代码支撑 | 方法论相似并不足以形成优势；必须在具体安克品类上运行，并给出可验证 Demo |
| 对对队 | 以 210 条真实用户评论结合睡眠声学和人因工程进行定量交叉验证，最终落到具体产品概念 | 公开样本必须形成跨来源、跨学科或实验层面的证据增量，不能只完成整理与审核 |
| 一锚定音队 | 聚焦“信号到立项决策”的可靠性机制，使用 20 余篇文献，完成数据源可及性实测和 Demo Run | 证据链、合议和人工授权需要转化为真实运行记录，并优先验证影响最大的模块 |

与本项目最相似的是 `token决定上限` 和 `一锚定音队`。这说明 Evidence-to-Decision、多 Agent、人工门禁和飞书协同的方向本身成立；差距主要出现在具体品类收敛、证据强度、实际运行和实验结果。

## 4. 我们做对了什么

1. 选择 Evidence-to-Decision，而不是一次性 Prompt-to-Idea。
2. 保留来源、置信度、Warning、Kill Criteria、Pending Confirmation 和人工决策责任。
3. 对 12 款安克产品、18 款竞品和 13 条公开用户反馈进行了结构化治理与人工审核。
4. 将飞书设计为证据、评审、PRD、任务和知识沉淀的协作底座，而不是末端导出按钮。
5. 明确披露本地 JSON、Proposal-stage Mock、无真实 LLM 和无实时前端飞书 API 的边界。
6. 交付了可运行七页前端、真实飞书工作区、数据分析样本和 Proposal PRD。

这些能力使项目具备继续发展的工程基础，但不能替代品类问题本身的验证。

## 5. 为什么当时没有充分考虑到

### 5.1 内部完成标准偏向系统完整性

当时的验收重点是七页路由、数据契约、状态一致性、飞书贯穿、风险边界和材料完整度。它们保证了项目专业、诚实和可维护，却没有把以下项目设为投稿前硬门槛：

- 目标用户一手访谈；
- 大规模评论或多来源交叉验证；
- 真实运行的 AI 决策切片；
- 产品核心价值实验；
- 已测量而不是仅提出的业务指标。

### 5.2 把“报名阶段 Mock”当成了可接受终点

Mock 对说明系统边界是必要的，但在同组选手已经提供实际代码、数据源实测、实验设计或端到端 Demo 时，Mock 只能证明交互与架构，不能证明 AI 原生方法有效。

### 5.3 平台叙事压过了产品叙事

项目投入大量篇幅解释工作台、Run 生命周期、Stage-Gate、Agent 委员会和飞书资产。最终候选“跨平台 Dock 兼容预检助手”的目标用户、关键任务、安克独有优势和产品实验没有获得同等展示权重。

### 5.4 缺少“同赛题相对竞争力”门禁

我们验证了方案是否自洽，却没有设置一个投稿前 Red Team Gate：假设同赛题已有多智能体、证据链和红队框架，我们还凭什么进入前三。若当时执行该门禁，证据深度和可运行验证会更早成为最高优先级。

## 7. 对当前项目的判断

本项目不应废弃，也不应继续通过增加页面证明价值。现有工作台适合作为 NPD 验证基础设施，下一阶段必须从“架构展示”切换为“单一产品问题的真实验证”。

北美市场选择本身不是问题。问题是当前缺少与北美定位相匹配的一手访谈、购买行为、设备拓扑和兼容任务实验，因此不能把市场标签当作市场证据。

飞书仍然是重要协作底座，但不再作为主卖点。主卖点必须是一个经过真实证据和实验验证的安克品类产品判断。

## 8. 后续开发原则

### Principle A: Product proof before platform breadth

先证明一个具体产品任务有效，再扩展多项目、更多 Agent 或更多协作资产。

### Principle B: Measured evidence before proposed metrics

把 Proposed Metrics 转成实测基线、实验结果和失败记录；未测量的指标必须继续标记为待验证。

### Principle C: One live vertical slice

至少跑通一条真实链路：

```text
用户设备与任务输入
  → 来源可追溯的兼容证据
  → AI / 规则联合判断
  → 支持 / 条件支持 / 不支持 / 未知
  → 人工确认
  → 结果与版本回写
```

### Principle D: Competition and stakeholder Red Team

每次外部提交前回答：

1. 如果竞争方案拥有同样的方法论，我们的不可替代证据是什么？
2. 是否存在真实用户、真实任务或真实实验？
3. Demo 展示的是已运行结果，还是仅展示未来流程？
4. 三分钟内能否先看懂产品价值，再理解平台能力？

## 9. 下一阶段验证门槛

当前进度（2026-08-05）：Page 6 已加入本地规则预检切片、10 条规则契约案例和验证运营控制台。后者已把 10 组拓扑与 3 类任务组合为 30 例金标准计划，并支持记录硬件测试或 FAQ 对照的浏览器本地待复核草稿；硬件金标准仍为 0 条，真实 AI 判断、一手访谈和已签核实测指标尚未完成。

在扩大功能范围前，主 Run 应完成：

1. 8–12 位目标用户的一手访谈或可复核任务观察。
2. 更大规模、多来源的公开评论语料，并保留正向或无故障对照，降低故障帖偏差。
3. 30–50 条人工金标准兼容案例，覆盖 Mac、Windows、Dock、线材和显示拓扑。
4. 一条真实运行的 AI / 规则联合判断链路，保留引用、版本、Unknown 和人工确认。
5. 实测金标准准确率、无依据确定性结论、任务完成率和排查时间。
6. 一个三分钟评审叙事：问题、证据、产品判断、运行结果、试点计划。

未达到这些门槛时，不新增展示性页面，不宣称产品验证完成。

## 10. 冻结边界

- 现有主 Run、13 条审核反馈、18 条 Gate 评审、6 个委员会角色和 Proposal PRD V0.2 继续作为历史投稿快照保留。
- 后续真实验证应创建新版本或新快照，不覆盖历史数据。
- 公开入围理由不构成安克内部意见，也不证明当前候选已被否决。
- 本复盘不恢复公开托管，不接入生产 LLM，也不改变敏感信息管理规则。
